Chapter 1

Warm Up

What the course is trying to teach, the one helper class that hides the window system, and the graphics Hello World: a rectangle, some shapes and text, the mouse, and a Paint program that draws polylines.

Follows the chapter Warm Up of Marlin Eller's Intermediate Java (sections Intro through Multi-Line Paint). The original is written for Java and IntelliJ IDEA; this page follows it in JavaScript in the browser and says where the two differ.

What this course is about

Eller's premise is that a beginning course teaches the materials (classes, loops, lists) and an intermediate one should teach buildings. The way to learn how a thirty-class program hangs together is to watch one get built, so the whole course is a narrated code review of a project he first wrote in 2005 and rebuilt for the class: a music notation editor driven entirely by pen gestures. The emphasis is on reading code and seeing it take shape rather than inventing it yourself, and you are expected to already know the basics: classes, static versus instance members, interfaces, ArrayList and HashMap.

The notes were written to be worked through at the pace of a class that meets twice a week for two hours, and the text carries Day 1 markers so you can see how far each session got. The same markers appear on these pages.

Project and packages Day 1

The Java project starts with four packages, and Eller spends some time on why: a directory structure is a filing system, and its only job is to make things easy to find later. His four folders are graphics for general 2D drawing helpers that could serve any project, reaction for the gesture framework (general, but not a traditional GUI, so it stays separate), music for everything that knows what a staff is, and sandbox for code he does not care about: experiments, throwaway tests, lesson demos. Anything worth keeping moves out of the sandbox.

This port keeps exactly that layout under src/, so the project map in the README reads the same as the course's package list.

Java → JavaScript. There is no IDE to install and no package statement to fix up. Each class is an ES module in a file of the same name, and the import lines at the top of every file do the job of Java's imports. There is also no build step: the browser loads the modules straight from the repository, which is why the whole site can be hosted as static files.

WinApp: the one window helper

Eller does not teach Swing. He hands you a single class, WinApp, that does all the window-system chores (create a frame, register itself as the mouse and keyboard listener, hand out a Graphics object) and then does nothing with any of it. Every program in the course extends WinApp and overrides the handful of methods it cares about: paintComponent, mousePressed, mouseDragged, mouseReleased, keyTyped. His point is that he is not teaching you to use menus and scroll bars but to write them, so the helper stays as thin as possible.

Java → JavaScript. Here WinApp wraps a <canvas> instead of a JPanel. The shape is the same: extend it, override the same method names, call repaint(). Two things are worth knowing. The canvas keeps the logical size you asked for in the constructor no matter how CSS or a high-DPI screen scales it, so all the course's pixel arithmetic still works. And mouse listeners become pointer events, which means a pen or a finger works the same as a mouse. The Graphics class is a small shim that maps the java.awt.Graphics calls the course uses (setColor, fillRect, drawLine, drawString, font metrics) onto the canvas context.

Testing WinApp: RedRect

The graphical Hello World is a class that extends WinApp and overrides paintComponent to fill one red square, 100 pixels in from the left, 100 down from the top, 100 wide and 100 high. That is the whole program. Eller uses it to make three points: every app needs the same boilerplate (extend the helper, write a constructor, override paint), the IDE will nag you about missing imports and you fix them, and the coordinate system has its origin at the top left with y growing downward, because computers were drawing text top to bottom long before they drew pictures.

The @Override lesson

The section ends with a long, useful digression. Misspell paintComponent as painComponent and Java compiles it happily: you have not overridden anything, you have defined a new method nobody calls, and the window stays blank with no error anywhere. Java's @Override annotation exists to catch exactly that, and Eller admits he often leaves it out because his IDE colors the intent for him. His real point is about writing for the humans who read the code later, not for the compiler.

Java → JavaScript. The trap is worse in JavaScript, because there is no annotation to ask for. A misspelled paintComponent is silently just another method. If a demo on these pages ever draws nothing, that is the first thing to check.

Paint: output, text, color and the mouse

From here on the course stops handing over whole files and gives fragments with the thinking behind them: "create me a WinApp named Paint" is expected to make you write the constructor, the main routine and a test paintComponent without being told. The next four sections then tour the basic drawing calls in that Paint app:

  • Swing Output. fillRect, drawRect, drawOval, fillOval and drawLine, all in "local coordinates" that the Graphics object translates to wherever the window happens to be on whichever screen. setColor is a state setting, so paint code is runs of "set a color, draw some things".
  • Text Output. drawString puts text on a baseline at (x, y), not in a box whose corner is at (x, y). To know where the text really landed you ask the font metrics for the ascent, descent and string width, which is what you will need later to tell whether a click hit a word.
  • Random Color. A color is three light levels from 0 to 255. This is where the grab-bag helper class G is born, with a random-number helper and rndColor(). Picking a random color inside paint has an ulterior motive: resize the window and the color flickers, which shows that the operating system, not you, decides when paintComponent runs, and that it runs it often.
  • Mouse Input. Override mousePressed to count clicks and the count on screen does not change, because nobody repainted. repaint() is how you ask the OS to call your paint code at its convenience. And the first thing every paint routine should do is clear the screen, because Windows does not do it for you and Macs do (the "Mac vs PC" aside).

All four sections are combined into one demo here. Click in it to bump the counter and note the random color changes on every paint.

Java → JavaScript. Clearing the screen matters here too: a canvas keeps whatever you drew last time. repaint() in the port asks for one paint on the next animation frame, the same "at the OS's convenience" contract as Swing, so the same bug (change state, forget to repaint, see nothing) is reproduced faithfully.

Polylines and the homework

A polyline is what you get from dragging a mouse: a sequence of points. Eller adds a static nested class Path that is just an ArrayList<Point> with one method, draw, which connects the dots, and uses it to explain why the loop starts at 1 (there is one fewer segment than points) and why he likes static nested classes (a helper that only its owner uses gets a two-part name like Paint.Path). Press starts a new path, drag adds points, and if you skipped the screen clear you will see every old path pile up on a PC and wonder how one variable holds them all.

The day's homework: one path is not a paint program. Add a Pic that is a list of Path and make the mouse code grow it. The spoiler is the last section of the chapter, and it is the demo below.

Java → JavaScript. Path and Pic extend Array the way the Java ones extend ArrayList. Every such subclass in this repo declares static get [Symbol.species]() { return Array; }: without it, map and filter would try to construct a new Path and hand it their arguments, which is not what a list subclass wants.
