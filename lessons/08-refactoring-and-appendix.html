Chapter 8

Refactoring & Appendix

Breaking the thousand-line music app into a package of small files, taking the application back out of the music code, and the appendix: parabolic splines, and an honest list of what neither the course nor this port finished.

Follows the last sections of Music Notes (Refactoring, Music2.java, The Music Package) and the whole Appendix chapter (Splines, Not Yet) of Marlin Eller's Intermediate Java. The course's notes stop mid-sentence at "still writing this course", so this page is partly about where the code ends and what would come next.

Why refactor at all

Everything since chapter 6 has gone into one sandbox class, Music1, with staffs, bars, heads, stems, beams and rests as nested classes inside it. Eller is blunt about how that turned out: the file passed a thousand lines and finding anything meant scrolling. His defence of it is the honest one. Code is never organized the way you wish it were, because the organization that seemed right at the start stops being right once the project has grown, and the moment you notice is usually the moment you cannot afford to fix it because version 1 has to ship. Version 2 is where you get to keep the good code and throw away the arrangement.

So the last act of the course is a rearrangement, not a rewrite. Not one drawing rule or bidding formula changes. What changes is who can see what.

Step 1: one class per file

Each nested class is cut out of Music1 and pasted into its own file in the music package: Bar, Beam, Duration, Glyph, Head, Page, Rest, Staff, Stem, Sys, Time. Two warnings come with it. The word static comes off every class header, because these were nested classes and are now top level. And when the IDE offers to fix the imports you must read what it proposes, because a Stem that used to mean Music1.Stem will happily be repaired into a reference back to the old sandbox class instead of the new neighbour that does not exist yet.

Java → JavaScript. This port was written file-per-class from the start, so Step 1 is already done everywhere and there is nothing to cut apart. The trap has an exact ES module equivalent though: an import that resolves to the wrong module is not an error, it is just a different class with the same name, and you find out when something draws in the wrong place.

Steps 2–4: the privacy sweep

The second step is the interesting one. Everything in Music1 was public, and Eller points out that this made no difference whatsoever: Java does not enforce access between nested classes, so privacy was a file-level idea, not a class-level one. Splitting the file into eleven files turns all of that into real access control, and the exercise he recommends is to mark everything private on purpose, watch the compiler light up, and then decide case by case whether the answer is "this really should be public" or "this needs a helper".

Both answers appear. Lists get helpers, so Time asks sys.addTime(this) rather than reaching into a list, and Staff gets its own index back from sys.addStaff(this) in one line. But a Time exists only to be a shared x value, and hiding that x behind a getter would be ceremony; his position is that getters and setters everywhere are just public fields with extra typing, and that deciding what is public is the actual work.

Step 4 is a design argument worth reading twice. Taking a head off a stem needs two things done: the head comes off the stem's list (and if it was the last one, the stem deletes itself) and the head's own stem and wrongSide fields have to be cleared. Splitting that work between Stem.removeHead and Head.unStem looks tidy, one class per set of fields, but it leaves a public removeHead that is not safe to call on its own, and in a year nobody will remember that. So he makes removeHead do the whole job and leaves a comment in unStem saying so. The port follows that decision, comment and all.

Steps 5–6: getting the application out of the music package

The real target of the refactoring is three application-level globals, PAGE, SYSFMT and SYSTEMS, which the music classes had been reading directly. A package that reaches up into one particular application cannot be reused by a second one, and worse, the globals bake in the assumption of a single page.

The fix is staged. First the singletons that plausibly belong to a page become members of Page (its system list and its format), and a Sys learns which page it is on, so Bar and Staff can reach both through sys.page. Then the formats stop referring to a page at all and take one as an argument, since a Staff.Fmt shared by many pages must not own any one of them. What is left over is the question of who decides whether there is one page or many, and that is the application's decision, not the music package's. So it becomes a contract: interfaces I.Margins, I.Page and I.MusicApp, plus a one-line class whose only job is to hold the app.

The names are chosen so that every reference from inside the music package reads the same way, which is the whole point:

APP.get.sysfmt(sys.page).maxH

The application now implements I.MusicApp and assigns APP.get = this in its constructor. The concrete Page class, having become a placeholder for a single-page program, is deleted; every page.top becomes page.top(). The new app is Music2, and Eller's two closing mistakes are the ones you would make too: he forgot to point Main at Music2 and was delighted that his enormous edit ran perfectly the first time, and then forgot the APP.get assignment and got a null pointer immediately.

Where this port stops

Plainly: this port does not do Steps 5 and 6. There is no Music2.js, no I.js, no APP.js. src/music ends at the course's single-page editor, here called MusicEd, with the later chapters' bug fixes already folded in. Page is still a concrete class that owns the margins, the system list, sysGap and maxH, and music classes that need a margin walk up to it: this.sys.page.margins.left. There is no Sys.Fmt either; the one thing it carried that we still need, maxH, lives on the Page.

That is a deliberate stop, not an oversight. The interface layer buys multi-page support, and this editor has one page and no way to make a second; adding the contract now would be a layer of indirection guarding a decision nobody is making. If a second application ever wants the music package, Step 5 is written down and waiting.

The same goals, reached differently

The refactoring has three goals underneath it: files small enough to read, a package boundary that is actually enforced, and confidence that a rearrangement of this size did not break anything. This port pursues all three, just not with interfaces.

  • The boundary is the import list. ES modules make the dependency direction visible at the top of every file, and here it only ever points one way: src/graphics imports nothing outside itself, src/reaction imports only from src/graphics, and src/music imports from both. Nothing in graphics or reaction mentions music, which is the property I.MusicApp exists to protect. A one-line grep checks it.
  • Files stay small by rule. No source file may exceed 800 non-empty lines, and a test enforces it, so the thousand-line Music1 could not have happened here. The largest file in src/music is about 140 lines.
  • The refactoring is testable. The course had no tests, which is why its refactoring advice is all about the compiler catching you. This repo has a headless suite instead: RecordingGraphics is a fake Graphics that records every drawing call so layout can be asserted without a canvas, and strokes.js synthesizes gestures so the whole editor can be driven from Node. Moving code between files either keeps those passing or it does not.

Appendix: splines

An editor like this eventually needs smooth curves — braces, ties, slurs, trills — and none of the tools so far can draw one. Lines and ovals are too rigid and the music font gives only fixed shapes. A spline is the third mechanism: you name the points the curve must pass through and the direction it must be travelling at each one, and the code invents everything in between.

Eller picks the parabolic (quadratic) spline over the usual cubic Bezier for a simple reason: the code is shorter, and the extra control a cubic gives you matters when a human is dragging control points, not when your own code is asking for a slur. Three points: the curve runs from A to C, and B is not on the curve at all. B's job is to supply both tangents at once, since AB is the direction the curve leaves A and BC is the direction it arrives at C.

The algorithm is recursion on midpoints, and it is pretty. Take the midpoint of AB, the midpoint of BC, and the midpoint of those two, call it ABC. That last point genuinely is on the curve, and it splits the problem into two smaller splines of exactly the same shape. Smoothness falls out for free: AB, ABC and BC are collinear by construction, so the tangent entering the join is the tangent leaving it. There is no multiplication anywhere, only sums and halves, which is why the method dates from machines where a divide was expensive and a shift was not.

Knowing when to stop is usually the hard part of a recursive curve routine, and the course sidesteps it: rather than measure flatness on every call and pay for the measurement whether or not it saves work, pass in a small depth like 4 and count down. That fixes the curve at 24 segments. It is the right trade here because both intended uses — tiny trill wiggles and long, barely-bent slurs — need very little subdivision anyway.

Splines know nothing about music, so they belong in G. There are two versions. G.spline draws its segments as it goes; G.pSpline appends them to the shared polygon buffer G.poly, which is what you want when a shape is several curves and some straight lines that all have to be filled as one outline.

The course tests it by dropping a random spline into Music2.paintComponent. Here it is a sandbox app instead: A and C are pinned, and clicking or dragging moves the control point B, with the two tangent lines drawn in grey so you can watch the curve leave A aimed at B and arrive at C as if it had come from B.

Java → JavaScript. The midpoints use idiv, not /. Every midpoint here was an int division in Java, and the recursion divides eight times over, so floating point halves would drift the vertices off the pixel grid the rest of the drawing code sits on. G.poly is a Polygon shim over the canvas path calls, with the same reset/addPoint interface the course uses.

Not Yet

The course ends here, and it ends honestly: the notes were being written while the class was being taught, the last two sections are titled "Not Yet" and "UnderConstruction", and the final line is that the course is still being written. Which means the splines never get used. Nothing draws a brace, a tie, a slur or a trill; the curve machinery is built and then the notes run out. Beyond that, everything a real notation editor needs is still missing: more than one page, saving and loading, printing, playback, lyrics, dynamics, accidentals beyond the key signature.

This port has its own list, kept in docs/STATUS.md rather than here so it can shrink without this page going stale. At the time of writing it is short: these lesson pages themselves, a review pass over the reaction and music packages, and a handful of small niceties — a touch-input check on phones, a debug toggle for glyph bounding boxes, and finding a job for the one recognized gesture that currently does nothing.

That is the whole project. The editor is in the next link, and everything it does — every stroke that becomes a staff, a note, a beam or a bar — came out of the eight chapters behind you.
