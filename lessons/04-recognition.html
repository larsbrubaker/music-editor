Chapter 4

Recognition

Turning a mouse stroke into a name. A bounding box, a fixed number of sample points, an integer coordinate transform, and nearest neighbor matching against a database of hand-drawn prototypes: the whole recognizer is about two hundred lines and no machine learning.

Follows the chapter Recognition Subsystem of Marlin Eller's Intermediate Java (sections PaintInk through Chapter Summary). The original is written for Java and IntelliJ IDEA; this page follows it in JavaScript in the browser and says where the two differ.

PaintInk, the test harness

The chapter opens by leaving the old Paint program alone and starting a new app, PaintInk, that will be the bench on which every piece of the recognizer gets tested. It grows through the whole chapter: first it just draws strokes, then it draws their bounding boxes, then their sample dots, then the prototypes it has collected, then the name of the shape the recognizer guessed.

Two classes appear with it. PL in G is a polyline, a fixed-size array of V with a drawN(g, n) that draws only the first n points, and Ink.Buffer extends it to capture one stroke: add appends a point up to UC.inkBufferMax (500), dn/drag/up are the I.Area methods so the app can hand the mouse straight to the buffer, and show draws what has been captured so far. There is exactly one of them, Ink.BUFFER: Eller makes the Java constructor private to say so out loud, because a second ink buffer would be a bug.

An Ink is what you keep after the stroke is finished. By the end of the chapter it is not a copy of the raw points at all but a Norm plus the VS box where the stroke happened on screen, which is both a compression (25 points instead of 300) and exactly the two things recognition needs.

Bounding Box Day 5

To scale a stroke you first have to know how big it is, so BBox tracks four numbers as two ranges, a horizontal LoHi and a vertical one. There is one deliberate lie in LoHi.size(): a range containing a single point reports a size of 1, not 0, because every use of it ends up as a divisor and a perfectly horizontal stroke really does have zero height.

Eller is careful about why BBox is not just a VS, even though both are rectangles. A BBox exists to grow as points arrive; a VS exists to hold a rectangle you draw in or scale to. Different behavior, different class, with getNewVS() to convert once the stroke is done.

The debug aid from this section survives in the port as a switch: Ink.Buffer.showBBox draws the box while you draw. Turn it on in the demo below.

Subsampling

How many points is a stroke? The honest answer is to print Ink.BUFFER.n on screen and find out, which is the lesson inside the lesson: when you want to know what your machine does, write code, do not go read opinions. A quick short line is about fifteen points; a slow screen-filling V is nearly four hundred.

Recognition needs to ignore three things: where on the screen the stroke was, how big it was, and how many points the mouse happened to deliver. Subsampling handles the third. The course walks past spatial, temporal and maximum-curvature sampling and picks the quick and dirty one, linear sampling by index: to get k points out of n, take

pl.points[i].set(this.points[idiv(i * (n - 1), k - 1)]);

It is a linear function that maps 0 to 0 and k-1 to n-1, so it lands on both endpoints and interpolates the indices in between. Too many points and it throws some away; too few and it duplicates some. UC.normSampleSize is 25, chosen by trying 10 (visibly too coarse: draw an a and watch it turn into a triangle) and then trying more.

PL.showDots is the other debug aid from this section, a blue circle on every sample point, and it is what makes the difference between the two sampling methods visible.

Java → JavaScript. The port defaults to a different subsampler. Pointer events on a fast flick can deliver five or six points for a whole stroke, and with n that small the index formula truncates several i values to the same index and piles most of the 25 output points onto the first sample, which no longer resembles the gesture. So Ink.Buffer.subSample normally calls subSampleByArcLength, which walks the cumulative length of the path and places 25 points evenly along it. The course's subSampleByIndex is still there and still used when Ink.Buffer.arcLength = false; the demo's index sampling checkbox flips exactly that flag, and tests/recognition.test.js exercises both.

Coordinate Transform

Where and how big are handled by one transform that maps any box onto any other box. There are no rotations here, so it is only a scale and a translate, four integers, and a single point moves like this:

(x', y') = (x * n / d + dx, y * n / d + dy)

The one scale factor n/d is the point of the section. Anisomorphic scaling, with separate factors for x and y, would stretch any rectangle onto any other and in doing so would erase aspect ratio, turning a nearly vertical slash into a perfect diagonal and a nearly horizontal one into the same perfect diagonal. Since the compass gestures differ from each other precisely by aspect ratio, the transform must be isomorphic: setScale takes the larger dimension of the old box and the larger of the new one, a "force fit" that guarantees the input lands inside the output box.

The offsets come from writing the obvious three-step recipe (translate the old center to the origin, scale, translate to the new center) and then using algebra to collapse it into one multiply and one add, which is what setOff returns. And the reason the multiply comes first is worth internalizing: with truncating integer division 17 * 4 / 5 is 13 but 4 / 5 * 17 is 0. Divide last, always.

Java → JavaScript. JavaScript has no integer type, so every place the Java relied on truncation the port calls idiv(a, b), which is Math.trunc(a / b). That is not decoration: setOff, V.blend and the index subsampler all depend on it, and the recognition tests assert the off-by-a-pixel results the truncation produces (a normalized stroke's endpoints land a unit or two inside the 0..1000 box, not exactly on it).

Norms Day 6

With subsampling and a transform in hand, a Norm is three lines of constructor: subsample the buffer into 25 points, set the transform from the buffer's bounding box to the normalized coordinate box NCS (0..1000 square), and transform. 1000 is picked so that squared distances stay in the millions, comfortably inside a 32-bit int.

A Norm cannot show itself, since it lives in an abstract coordinate system, but it can drawAt(g, vs) by running the transform the other way. That is how Ink.show works, and it is also how prototypes get drawn into little boxes at the top of the screen.

The one measurement everything else is built on is dist: sum, over all 25 points, of the squared x and y differences. No square root, because the result is only ever compared against other distances and against UC.noMatchDist (500000). Two strokes of the same shape score small; a V against an L scores large. PaintInk prints the distance between the last two strokes in black or red depending on which side of that threshold it falls on, which is how the number got chosen in the first place.

The threshold is really the recognizer's willingness to guess. Nearest neighbor matching on its own always returns something; capping it at noMatchDist lets the answer be "I do not know". Err on the small side: an honest null costs you a few more training examples, a wrong match costs you a wrong note.

Shape and Prototype

A Shape is a name plus the list of ways that shape can be drawn. An O can be drawn clockwise or counter-clockwise, and each of those actual ways is a Prototype, which is a Norm with a blend count.

Blending is the incremental average trick: if you already hold the average of k values and a new one arrives, the new average is (k * old + new) / (k + 1). V.blend does it for one point, Norm.blend for all 25, and Prototype.blend passes its own nBlend and increments it. So every extra example you draw quietly smooths the stored prototype rather than piling up near-duplicates.

Prototype.List.bestDist(norm) is the search: it returns the distance of the closest prototype and, as a side effect, leaves that prototype in the static bestMatch. Starting bestSoFar at noMatchDist means a list with nothing close enough simply returns no match. Prototype.List.show marches a 60-pixel showbox across the top of the window drawing each prototype with its blend count above it (the port also puts a red dot on the first point, so you can see which end of the stroke was the start).

PaintInk uses all of this even before there is a database: every stroke either blends into a matching prototype or becomes a new one, and then the ink on screen throws away its own norm and points at the prototype instead. Draw the same letter five times and all five copies on the page redraw themselves as the shared prototype gets smoother. It is a smoothing trick, a compression trick and a very direct picture of what the recognizer thinks your handwriting looks like.

Refactoring & Renaming

A short aside with a long tail. Renaming used to be manual work, and the compiler would catch every reference you forgot; what it never caught, then or now, is the comments. That is why old comments are untrustworthy, and why Eller's rewrite of these notes renamed things in the earlier chapters so the text and the code agree. His conclusion is a good working attitude: the code gets to decide how it wants to be organized, and the effort of changing it is not an argument.

This port inherits the same duty. Every source file's comments were written against the code as it stands, and where JavaScript forced a difference the comment says so on the spot rather than in a document that can drift.

ShapeTrainer Day 7

To test matching across a whole database, you first need a database, so the chapter builds the tool that makes one. The trainer is PaintInk with a name attached: type a shape name, draw examples of it, and each stroke is blended into or added to that shape's prototype list.

  • DOT. One shape is never trained. A press and release in the same spot has a tiny bounding box and no real path, so blowing it up to 0..1000 would normalize pure noise. Shape.recognize therefore checks the ink's vs against UC.dotThreshold (5 pixels) first and answers Shape.DOT without looking at the norm at all. Note what this implies: recognition takes an Ink, not a Norm, because it needs the box as well as the shape.
  • Legal names. That makes "DOT" an illegal name to type, and so is the empty string. The trainer reports the typed name as KNOWN, UNKNOWN or ILLEGAL and refuses to train the last of those.
  • Saving. Deferred in the course to the serialization section, then wired to the Enter key.
  • Selection buttons. Left for later: there is no browse-the-database UI, you see a shape's prototypes by typing its name.
  • Deletion buttons. The course wants them, admits it would need areas and buttons that do not exist yet, and assigns them to a hypothetical intern. This port implements the poor man's version: end a stroke in the showbox strip along the top and the prototype under it is removed (Trainer.removePrototype turns the x coordinate into a box index with idiv). The course's fallback, quit without saving and lose everything, also still works.
  • Keyboard. The first keyboard input in the course. keyTyped appends characters to the current name; space or Enter clears it. The port also handles backspace, which the course leaves as a thing to look up when you need it.

The Shape Database

The database is a map from name to Shape. A list would do for recognition, which just scans everything, but the map is what the music editor will want: a reaction is registered against a name like "S-S", and the recognizer hands back the shape with that name.

Database wraps the map so it can own the small rules: forceGet always returns a shape, creating it if this is the first example; isLegal rejects the empty name, DOT, and anything with whitespace in it; train(name, norm) checks legality and forwards to Prototype.List.train, which blends or adds. That last refactoring is the point of the section. Moving training out of the app and into Shape is what will later make it possible for an application to notice that a gesture it needs is missing and ask the user to draw a few.

Java → JavaScript. The Java Database extends TreeMap, so it is sorted; the port extends the built-in Map, which is insertion-ordered. Nothing depends on the order. What did need care is Shape.LIST: in Java, DB.values() is a live view that can be stored in a static field once, but in JavaScript values() returns a one-shot iterator, so Shape.LIST is defined as a getter that calls it fresh each time.

Serialization, or a JSON file instead

The course reaches for Java serialization: mark the classes Serializable, write the one top-level object to a stream, read it back. Eller then spends a page on the warning that comes with it, and it is the right warning. A serialized graph breaks the moment you add a field, and it is not a format you can hand to another machine. Serialization there is a development convenience, not a file format.

Java → JavaScript. The port takes the warning's advice and writes a real format instead: a small JSON document, { version, shapes }, where each prototype is its blend count and its fifty integers. Database.toJSON and mergeJSON are the two halves, and merging deliberately keeps existing Shape objects and replaces only their prototype lists, because reactions will be holding references to those shapes. Saving goes to localStorage under UC.shapeDatabaseFileName rather than to a file, guarded so that Node tests can call the same code with no browser present.

There is a second difference that matters more. Nothing ships a serialized file here, because a baseline database has to exist before anyone has trained anything. scripts/gen-shapes.js generates assets/shapes.json by pushing synthetic strokes through the real Ink → Norm → Database.train pipeline, so the stored prototypes are exactly what the trainer would have produced by hand: ten compass gestures, several at different aspect ratios, plus an O drawn each way round. Shape.loadDefaults fetches that file and lets anything you trained in this browser win over it. The editor's sidebar can download the current database, load one back, or reset to the shipped defaults.

Test Recognition & Refactoring Day 8

With a trained database, PaintInk gets its last line: run each finished stroke through Shape.recognize and print the name, or UN-RECOGNIZED when nothing was close enough. Draw a few gestures in the demo above and watch it; then draw something ridiculous and watch it correctly refuse.

The chapter closes by looking at the trainer's mouseReleased, deciding it is far too long, and moving nearly all of it into a new Shape.Trainer. What is left in the ShapeTrainer app is a handful of one-line overrides that forward to Shape.TRAINER and call repaint(), which only a WinApp can do. The trainer implements I.Show and I.Area, which is the same pair of interfaces everything else in the system uses, and that is what will let the finished editor flip between the music view and the training view with one boolean.

Java → JavaScript. All of this is testable without a browser, and it is tested. tests/recognition.test.js drives the real classes with synthetic strokes: both subsamplers, the 0..1000 normalization, distance between same and different shapes, blending, recognition of every shipped gesture with jitter at various sizes and positions, the DOT special case, the JSON round trip, and the trainer typing a name and deleting a prototype. There is also a regression test for the arc-length change: a stroke made of only a few mouse samples must still recognize.

Summary

That is the whole recognizer: a bounding box, subsampling to a fixed 25 points, an integer isomorphic transform into a 1000-unit square, squared Euclidean distance, nearest neighbor with a refusal threshold, incremental averaging to smooth prototypes, and a trainer to collect them. No libraries, no training run, and small enough to read in one sitting. With recognition working, the next chapter can build the framework that decides what a recognized gesture should do.
