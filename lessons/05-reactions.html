Chapter 5

Reactions

The four small classes that turn a recognized stroke into something happening: Gesture, Layer, Reaction and Mass. A marketplace where every interested object bids on the gesture and the lowest bid wins, a test app of boxes you can draw and delete, and undo for almost nothing by replaying the gesture list.

Follows the chapter Reactions of Marlin Eller's Intermediate Java (sections Outline through OTO Afterthoughts). The original is Java; this page follows it in JavaScript and says where the two differ.

The four classes, and what each one is for

Recognition is done: a stroke goes in and the name of a shape comes out. Nothing yet happens as a result. This chapter builds the machinery that connects the two, and it is only four classes, each with one job.

  • Gesture is what was done and where: a Shape plus the VS box the ink occupied. It is Ink with the ink thrown away. Ink remembers 25 resampled points and therefore remembers which direction you drew in; a Gesture has already been reduced to "an S-S happened, here". Thirty gestures are thirty little objects all pointing at the one shared Shape named "S-S".
  • Layer is z-ordering. Drawing goes back to front, so a layer holds everything that sits at the same depth, and drawing the screen is drawing the layers in order. There is one special layer, ALL, whose members are the other layers.
  • Reaction is a pair of functions attached to a shape name: bid says how much you want this gesture, act does something about it.
  • Mass is a thing on the screen that can react: it lives in a Layer so it can show itself, and it owns a list of Reactions so it can respond.
Java → JavaScript. The course keeps its interfaces in one class, I: I.Show, I.Act, I.React, I.Area. There is no I.js in this port because JavaScript has no interfaces and does not need them: anything with a show(g) method can go in a Layer, anything with hit/dn/drag/up is an area. The comments in the source still name the interface the object is standing in for, so the two read side by side.

Reaction: the marketplace

A Reaction knows one Shape, looked up by name in the shape database at construction time. If the name is not in the database you get a console complaint and a reaction that will wait forever for a stroke that can never be recognized — try it by asking for a shape called "BUG".

Every reaction lives in two places at once, and understanding that is most of the class. It is on the Reaction.List of the Mass that created it, so that deleting the Mass can take its reactions with it. And it is in the byShape map, from a Shape to every reaction currently interested in that shape, so that when an S-S is recognized only the S-S reactions are consulted. Being in the second place is what enable() and disable() mean; a Mass can keep a reaction on its own list but withdraw it from the market.

The auction itself is six lines. loBid walks a list, asks every reaction to bid, and keeps the lowest number. Low bids win because a bid is a distance: zero is a perfect match and larger means less appropriate. The starting value for "best so far" is UC.noBid (10000), which doubles as the way a reaction refuses to play at all:

noBid: 10000,             // a reaction returns this when it does not want a gesture

A bid of noBid can never beat the initial best, so a refusing reaction is simply not in the contest, and if everyone refuses loBid returns null and nothing happens. Reaction.best(gest) is then the one public entry point: look up the gesture's shape, run the auction on that list, hand back the winner or null.

This one convention carries the whole rest of the project. Every music object in the later chapters bids some function of the distance between the gesture and itself, so "the note nearest where you drew" wins without anybody keeping a hit-test tree or a selection.

Java → JavaScript. The course makes each reaction an anonymous subclass of the abstract Reaction, supplying bid and act in braces after the constructor call. Here you pass the two as arrow functions to the constructor instead: new Reaction('S-S', (g) => ..., (g) => ...). The result is the same object with the same two methods, and the arrow function's closure does the job of Java's compound Box.this for reaching the owning Mass (see the demo below). Reaction.List extends Array where Java extended ArrayList, and like every list subclass here it declares static get [Symbol.species]() { return Array; } so that map and filter do not try to build a new ReactionList. Reaction.Map extends the built-in Map, which already keys on object identity, so getList is the same get-or-create helper the course writes.

Layer, and a bug the course leaves in

Layer is an eight-line class: a named list of showable things, a show that loops over them, a static byName map, and the static ALL layer that every new layer adds itself to. Note that ALL holds Layers, not Masses. All Masses live in layers, but not everything in a layer has to be a Mass.

Eller deliberately publishes this class with a bug and then explains it, because it is a bug you cannot easily debug: he declared ALL before byName, and constructing ALL writes into byName, which does not exist yet. Static initialization looks automatic but it is just code running in source order, and code has ordering dependencies. The fix is to swap the two lines.

Java → JavaScript. The same hazard is real here and the port keeps the fixed order with a comment saying why: static byName is declared before static ALL, since class static fields are initialized top to bottom. The constructor also guards with Layer.ALL &&, because the very first layer built is ALL and it cannot add itself to a field that is still being assigned. Two methods are additions for the browser: Layer.ensure(name) get-or-creates, so several demos on one page can each ask for a "BACK" layer, and resetAll() throws the layers away when a page switches apps.

Mass, and a bug that JavaScript does not have

Mass is a Reaction.List and lives in a Layer. Its constructor takes a layer name, finds the layer and adds itself; deleteMass() calls clearAll() to pull every one of its reactions out of the marketplace and then removes itself from its layer. Its show is deliberately empty rather than abstract, so a Mass that only reacts and never draws costs you nothing.

The course pauses here to fix a bug out of order, because it is the kind that surfaces years later and wastes days. Java's ArrayList.remove uses equals(), and if two different Masses ever compare equal by value the list removes the wrong one. The fix is to force referential equality with a one-line equals, plus a unique hashCode, since the collections require the two to agree.

Java → JavaScript. That fix has no JavaScript counterpart and the port says so in the file header. indexOf on an array uses strict equality, which for objects is already reference identity, and there is no way to override it. The port's removeItem and the removeFrom helper in Reaction do indexOf plus splice, which is exactly the behavior the course had to work to get.

Gesture and the one shared AREA

The Gesture class itself is a constructor and a factory: getNew(ink) recognizes the ink and returns a Gesture, or null if nothing matched. The interesting part is the static Gesture.AREA, the mouse behavior every reaction-based app installs. dn and drag just feed Ink.BUFFER. up is the whole pipeline in ten lines: close the ink, build an Ink from the buffer, try to recognize it, clear the buffer, and if a shape came back run the auction and let the winner act.

Two different things can go wrong, and while you are developing you want to know which. So Gesture keeps a static string, recognized, set to the shape name or "null" when nothing matched, with " no bids" appended when a shape was recognized but no reaction wanted it. Any app can put that on screen with a single drawString. Eller notes this is a design improvement over where he first put the debug message: instrumenting the framework once beats instrumenting every app.

A simple reaction test

Now the smallest possible application built on all of it. ReactionTest creates two layers, adds one reaction to Reaction.initialReactions looking for SW-SW, wires the three mouse methods straight through to Gesture.AREA, and paints by clearing the background, showing Layer.ALL, showing the ink buffer on top, and printing Gesture.recognized. That reaction bids 0 — a perfect, unbeatable bid — and acts by making a Box the size of the ink.

Boxes then carry their own reactions. An S-S adds a delete reaction whose bid is the interesting part: take the hot spot of the stroke (top middle), refuse with noBid if it did not land inside this box, otherwise bid the horizontal distance from the stroke to the box's center. That is the shape of nearly every bid function you will write: a test that rules the gesture out entirely, and otherwise a number that shrinks as the match gets better.

Using only the x distance is a deliberate demonstration. Draw a big box, then a small box on top of it off to one side, and do the delete stroke inside the small box but nearer the big box's center — the big one goes, out from under the little one. Bidding is a negotiation between everything on screen, not a hit test on the topmost thing. The alternative, a constant bid, means the first reaction on the list always wins no matter where you drew.

The homework was a second reaction, so a DOT on a box recolors it. It is in the demo.

Java → JavaScript. This is where the anonymous-inner-class trick and its compound this would appear in the Java. Compare Box.this.vs.hit(x, y) with the port's this.vs.hit(x, y) inside an arrow function: an arrow function has no this of its own, so the this it sees is the enclosing constructor's Box, which is precisely what Box.this meant. The one thing to watch is that this only works with arrow functions; a function expression there would be bound to whoever called it.

Undo, by replaying everything Day 9

Undo in a normal application is hard: you write the code to do a thing and then a second body of code to un-do it. Here it is nearly free, because every change to the document came from one gesture. Keep the list of gestures; to undo, drop the last one, wipe the world back to its starting state, and replay the rest.

That is Gesture.undo(): pop the undo list, Layer.nuke() to empty every layer (and with it every Mass), Reaction.nuke() to throw away byShape and re-enable the app's initialReactions, then replay. Replay needs a second path that does not push onto the undo list, hence the pair doGesture (auction, record, act) and redoGesture (auction, act). AREA.up hard-wires one shape, N-N, to undo itself, which does mean no reaction can ever see an N-N.

Two consequences are worth taking seriously, because the music chapters inherit them. There are now two paths through the code, one with a repaint after each gesture and one with none, so drawing routines must have no side effects: anything you compute in paint and stash for later will behave differently on replay. And replay must be deterministic. ReactionTest violates that on purpose — its box colors are random, so every undo repaints the world in new colors, which is a memorable way to learn the rule.

Undo is a good thing to test headlessly, and tests/reaction.test.js does: it drives Gesture.AREA with synthetic strokes, checks that the closer box wins the delete auction, then undoes with N-N strokes and asserts that the deleted box comes back and that the layers empty out as the list drains. No canvas involved.

Java → JavaScript. One addition the course does not need: World.reset(). A Java app owns its process, so the static byShape map, Layer.ALL and the undo list are fresh at startup. On a lesson page several reaction apps share one browser tab and therefore share that static state, so every app's constructor calls World.reset() first to forget the previous app's layers, reactions, undo list and ink.

What works, what does not

With undo running, the reaction framework is essentially finished, and Eller stops to list what is missing. The area system is a kludge — one area for Ink, another for Gesture, no way to keep a list of areas and choose between them — and until that is fixed there can be no draggable handles that resize a thing without leaving ink all over the screen. He also wants "one-time offers": a suggestion that appears, and vanishes the instant you do anything else, instead of a dialog you have to dismiss. Both are deferred. The tools are good enough; time to build the music application.

Afterthoughts Day 10

He then cannot resist designing the one-time offer anyway, on paper. The reasoning is a nice tour of the architecture: only one is ever needed, it must be a Mass because it draws and reacts, but it need not be created and destroyed — it can live permanently in the top layer and use an enabled flag to draw nothing and bid noBid when it is off. Dismissing it happens after the winning reaction is collected, and because there are two paths through the code it has to be dismissed in both doGesture and redoGesture. Nothing is implemented; nothing in this port implements it either. The point that survives is that living in a layer does not mean being visible or reactive.

The chapter closes by going back and adding something to the Shape Trainer from the previous chapter: deleting a bad prototype. He had told the class it was too hard, and then noticed it was a handful of lines. The prototype thumbnails march across the top of the screen at algorithmically regular positions, so if a stroke ends up in that strip, ignore the ink entirely, divide the x coordinate by the box size to get an index, and remove that prototype. That code is in src/reaction/Shape.js as Trainer.removePrototype, called first thing in the trainer's up, and you can use it in the trainer demo on the previous page.
