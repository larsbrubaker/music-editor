Chapter 2

Basic Graphics

The little helper classes that the rest of the project is built out of (V, VS, LoHi, BBox, PL), the interaction tricks every graphics program needs (hit detection, rubberband rectangles, dragging with an offset), a detour through splines and animation, and the refactoring that turns an if-statement into two classes: Areas.

Follows the chapter Basic Graphics of Marlin Eller's Intermediate Java (sections Intro through Squares.java). One toy app, Squares, is grown step by step through the whole chapter; this page follows it in four demos.

Growing G: V, VS, LoHi, BBox, PL Day 2

Chapter 1 ended with G holding two throwaway helpers, a random number and a random color. Eller's rule for it is that nothing goes in until a program actually needs it: G is your bucket, not his. Then he breaks his own rule just far enough to name the five nested classes he knows are coming, so you can see the shape of what is ahead:

  • V is a point, the equivalent of awt.Point, but named for "2D vector" because you will add them together.
  • VS is a rectangle held as two vectors, a location and a size. It is where hit detection lives.
  • LoHi is a pair of ints, a low and a high. It works in two directions: grow it to swallow every value you feed it, or use it to clamp a value into range.
  • BBox is two LoHi ranges, horizontal and vertical. Later it will measure a scribble so the scribble can be scaled to a standard size.
  • PL is a polyline, the class the Path in Paint should have been.

The advice around this list is worth as much as the list. When you write a program you usually do not know where code belongs, and that is fine: write it in the sandbox where it is needed, and when you catch yourself writing it a second time somewhere else, that is the signal to lift it into G. Small and reusable goes in G; anything more specific extends a G class instead.

Java → JavaScript. In Java these are static nested classes, so their names are G.V, G.VS and so on. Here each is a top-level exported class in the one G.js module, and the last line of the file re-attaches them (G.V = V; G.VS = VS; ...) so that code ported from the course can keep writing new G.V(0,0) and read the same. The other constant worry is integer math: Java's / on ints truncates, and formulas like VS.xM() and the spline midpoints depend on it, so the port calls idiv() from the same file everywhere the Java divided ints.

Hit detection, and Squares the app

Hit detection is done on rectangles because a rectangle makes it trivial: the mouse hit if its x is between left and right and its y is between top and bottom. That is the whole of VS.hit. The other addition here is fillBack, which fills a 3000×3000 white rectangle, because a paint routine nearly always wants to start by clearing the panel. Eller points at his own two magic numbers and leaves them in on purpose; cleaning up magic numbers is a section later in this same chapter.

To test the new code he starts a new sandbox app, Squares: one VS, one color, a paintComponent that clears and fills it, and a mousePressed that re-rolls the color only if the press hit the rectangle. Click inside the box below and it changes; click outside and nothing happens, which is exactly the assertion being tested.

Many squares and rubberband rects

One rectangle is not an app. A VS has no color, so Squares gets its own nested Square extends G.VS that adds one, and a Square.List that knows how to draw itself: the same pattern as Paint.Path and Paint.Pic in chapter 1. Now every click appends a new 100×100 square in a random color.

Eller stops here for an aside about where code belongs. He notices that mousePressed says squares.add(new Square(x,y)) and that he could push that into the list as addNew(x,y), simplifying the caller by complicating the class. Which is right? Neither, is his answer: there is no BEST placement, only BETTER and GOOD ENOUGH FOR RIGHT NOW, and the OO instinct that some single correct arrangement exists is simply wrong. The port keeps addNew on the list so you can see both versions.

"Rubberband" is the old name for something you stretch with the mouse while you watch it. The change is small: on press, create the square and remember it in lastSquare; on drag, call resize on that square. resize guards against the mouse going above or left of the corner, so dragging backwards leaves the square alone rather than producing a negative size.

Dragging boxes Day 3

Next the app learns two behaviors instead of one: press on empty space and you rubberband a new square, press on an existing square and you drag it. Two pieces make that work. Square.List.hit walks the whole list and returns the last square that was hit, not the first, because squares are drawn in list order and later ones cover earlier ones, so the last hit is the one the user sees on top. (A student's alternative: walk the list backwards and return on the first hit.)

The other piece is the gotcha the section is really about. If dragging moves loc to the mouse, the box jumps so its upper-left corner snaps under the cursor. To make the box stay stuck where you grabbed it, record the offset from the corner to the press point once, in a mouseDelta, and add it back on every drag. Ugly in English, one line in code.

Java → JavaScript. Two differences. The course's fields are static, because a Java program has exactly one PANEL; here they are instance fields, since a lesson page can mount and unmount several apps, and this.squares reads the same as Squares.squares did. And SquareList extends Array the way the Java extends ArrayList, so like every list subclass in this repo it declares static get [Symbol.species]() { return Array; }, otherwise map and filter would try to build a new SquareList from their arguments.

Sidebar: splines

This section is explicitly a detour: the course never needs curves, and the full explanation of why splines work is in the appendix. But the squares app has accidentally become the perfect spline demo, because a spline demo needs three handles you can drag around, and we just built draggable handles. A parabolic spline draws a curve from A to C, bent by a control point B. The implementation is four lines of recursion and no math: take the midpoints AB and BC, take the midpoint of those two, and the problem becomes two smaller splines. When the recursion counter hits zero, draw a straight line.

Both of the remaining demos on this page draw a spline through their first three squares, so the "Show spline" checkbox is on each. Draw three boxes, then drag them around and watch the curve follow.

Animation, and a game

Another sidebar, this one for the people who came to write video games. Animation is nothing but drawing one slightly different picture after another, so all it takes is a per-frame update and something to call it. The update is vector addition: give each square a velocity dv and add it to loc every frame, which is why V got an add method back at the start of the chapter.

Eller deliberately makes the motion a side effect of drawing, and says up front that this is bad structure. His reason is good: as long as moving happens inside painting, you can force a frame by hand by grabbing the window corner and shaking it, which is the poor man's animation timer and makes the whole thing easy to debug before any timer exists. Squares that fly off screen never come back, so next comes bouncing: if a square has crossed a wall and its velocity still points that way, flip the sign of that component. Testing the corner is wrong for the right-hand and bottom walls, and the fix goes into VS rather than into the bounce code, as the six accessors xL/xM/xH and yL/yM/yH — low, middle and high in each direction — because these come up constantly once you start doing layout.

Then the timer. A Swing Timer takes a delay in milliseconds and an ActionListener, and calls actionPerformed on it forever; 30 ms is about 30 frames a second, and the listener here just calls repaint(). Finally the game: pressing on a square already records it in lastSquare, so zero its velocity and it stops. Remember where the press happened, and on release set the velocity from the press point to the release point, so a flick launches the square off in a new direction. Miss your target and you have created a new moving square instead, which is the whole difficulty of the game.

Java → JavaScript. The port has its own Timer in WinApp.js with the same surface (new Timer(30, listener), setInitialDelay, start, stop) built on setTimeout for the initial delay and setInterval after that. There is no ActionListener interface to implement, so the app passes a plain object, { actionPerformed: () => this.repaint() }; the arrow function is what keeps this pointing at the app, the job Java did by having the class implement the interface itself. The timer starts in mount rather than in the constructor so that a demo which is never run never animates.

UC and I

Two naming conventions, both instances of the same idea: collect a category of small things into one file so they are easy to find and so their names announce what they are.

I is a single interface whose only job is to contain all the other interfaces as nested ones. The payoff is that every interface in the project is spelled I.Something — I.Draw, I.Hit, I.React — which reads better than Java's own MouseListener/MouseAdapter style and lets a class Foo implement I.Foo without a name collision.

UC, Universal Constants, is the same trick for magic numbers. The usual advice is to name each constant static final in the class that uses it, and Eller's objection is organizational: the day someone asks for a settings panel, you have a hundred such names scattered over dozens of classes. So they all live in UC under long globally-meaningful names, and a class that wants a short local name just aliases it. This is why the window size was hardcoded as 1000 by 800 until now; from here on it is UC.mainWindowWidth.

Java → JavaScript. There are no interfaces in JavaScript, so there is no I.js in this port. I.Area and the rest survive as a duck-typed convention: an object is an I.Area if it has hit, dn, drag and up, and the comment above such a class says so (see the top of Squares.js, Ink.js and Gesture.js). Nothing checks it for you, which is exactly the price you pay for the convenience. UC is a plain exported object rather than a class of static final fields; the constant list runs ahead of this chapter because later chapters keep adding to the same file.

Areas: two classes instead of one if-statement

Now the refactoring that this chapter has been building toward, and the one idea from it the music editor depends on. Compare Paint with Squares: Paint did a single thing on press and drag, so its handlers were one line each. Squares has to ask which of two behaviors it is in, so it needs a dragging boolean set in one method and tested in another. With two behaviors that is merely annoying. The editor will want at least four — gesture ink that vanishes on release, real ink that stays, dragging a handle with no ink at all, and buttons that fire on release only if you both pressed and released on them — and at four the branching is unmanageable.

The design: cover the screen with rectangular Areas. On press, find the area that was hit, make it current, and hand it the whole gesture. An area is anything with hit(x,y), dn(x,y), drag(x,y) and up(x,y). In the finished editor almost the entire screen will be one big gesture area, with a few handles and buttons sprinkled on top of it.

Squares needs two areas. Dragging is triggered by clicking a square, so Square itself becomes the area: hit it already inherits from VS, dn records the mouseDelta, drag moves the square, and up does nothing. Rubberbanding needs an area that covers everything, so a single 3000×3000 white BACKGROUND square goes in at the front of every list, and its dn and drag create and resize a new square instead. Because there is exactly one of it, Java builds it as an anonymous class: new Square(){ ... } with a brace block that overrides just those two methods for this one object.

The scorecard is honest. The code did not get shorter; there is an extra interface and an extra class, and the file is longer than before. What got shorter is mousePressed, which is now readable in one breath: find the area, tell it the mouse went down, repaint. And the behaviors are separated, each class doing one thing, which is what makes a third and fourth behavior cheap. The general lesson: when you see if-statements branching on which behavior you are in, ask whether those branches want to be classes.

Java → JavaScript. JavaScript has class expressions, but the simplest equivalent of the anonymous BACKGROUND square is to build a normal AreaSquare and then overwrite two of its methods on that one instance: bg.dn = (x, y) => {...}. The arrow functions do a second job as well. The Java anonymous class reaches its enclosing app through Squares.this and static fields; here the arrows simply close over app, and ordinary squares get the same reach by holding an app reference, since without statics they need some way back to the shared mouseDelta and lastSquare. One consequence to watch in paintComponent: the spline uses squares 1, 2 and 3 because index 0 of every list is BACKGROUND.
